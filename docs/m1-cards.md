## M1-01 — product-каркас и закреплённый стек

Статус: завершено. Фактический результат и проверки —
`docs/m1-01-product-skeleton.md`.

Цель: создать новый solution модульного монолита на .NET SDK 10.0.401 / Runtime
10.0.12 и frontend из решения M0-05. Результат: Domain, Application,
Infrastructure.Sqlite, Web, Client и тестовые проекты; `/api/v1/health`, static SPA,
runtime config для base path, версия app/API/schema, `global.json`, NuGet/pnpm lock,
THIRD-PARTY-NOTICES и генерация self-contained ZIP.

Проверки: UI и API 200; неизвестный API 404 JSON; клиент работает из корня и под
URL-префиксом; ZIP запускается из пути с пробелами/кириллицей без установленного
.NET/Node; frontend не делает внешних запросов. Ошибка несовместимого браузера
показывается по feature detection. Не входят SQLite, предметная модель и LAN.

## M1-02 — владение `dataRoot` и локальная сессия

Статус: завершено. Фактический результат и проверки —
`docs/m1-02-local-session.md`.

Цель: исключить два server writer для одного каталога. Результат: межпроцессная
блокировка по final filesystem identity/каноническому пути на весь срок процесса;
UNC/network roots запрещены, разные локальные roots разрешены. Защищённая запись
сессии позволяет повторному запуску открыть существующий URL; при невозможности
проверить владельца показывается ошибка. Изменяющий API разрешён только POST/PUT/
PATCH/DELETE, требует session token, отдельный CSRF nonce, точный Host/порт,
допустимый Origin и JSON content type; CORS отключён.

Session token и nonce криптографически случайны, не передаются в URL/referrer и
не попадают в журналы; защищённая запись сессии доступна только текущему
пользователю Windows. В карточке явно задаются срок и ротация CSRF nonce.

Проверки дочерними процессами: абсолютный/относительный путь, регистр, junction и
8.3 alias одного root дают один lock; иной root работает; аварийно завершённый
процесс освобождает реальную блокировку. Изменяющий GET, чужой Host/Origin,
неверные session token/CSRF nonce отклоняются. Повтор command ID проверяется в
M1-06, session token не является одноразовым. Не входит LAN-блокировка.

## M1-03 — SQLite и транзакционный каркас

Статус: завершено. Фактический результат и проверки —
`docs/m1-03-sqlite-storage.md`.

Результат: `app.db` только в `dataRoot`, foreign keys включены, `schema_history`,
один transaction/unit-of-work API, busy timeout, корректное закрытие соединений и
layout поколений для будущей candidate-миграции. БД открывает только сервер.

Проверки: данные переживают перезапуск; исключение откатывает команду полностью;
FK запрещает сироту; принудительный второй writer не оставляет половину записи;
SQLite version присутствует в diagnostics. Предметных таблиц ещё нет.

## M1-04 — проекты и жгуты

Статус: завершено. Фактический результат и проверки —
`docs/m1-04-projects-harnesses.md`.

Результат: стабильные UUID для Project/Harness; обозначение и инкремент проекта,
количество партии, ручной статус, упорядоченный список жгутов; команды создать,

копирование не меняет источник. Объекты, Э4 и графика не входят.

## M1-06 — команды, ревизии и автосохранение

Статус: завершено. Фактический результат и проверки —
`docs/m1-06-commands-autosave.md`.

Результат: command ID, expected project revision, журнал команд/версий и одна
SQLite-транзакция на принятую сервером команду; read model открытия проекта.
Подтверждённая ответом команда сразу долговечна. Debounce 1–2 с разрешён только
для отправки объединяемого клиентского черновика; UI различает pending/acknowledged,
на сервере одновременно выполняется не более одной записи проекта.

Проверки: повтор command ID идемпотентен; stale revision даёт стабильный конфликт;
сбой посередине не публикует часть; после kill/restart сохранены все acknowledged
revision, неотправленный pending draft может быть потерян и так обозначается.
Ctrl+Z редактора входит в M3, производственный факт — в M8.

## M1-07 — единицы и EX-01

Статус: выполнено в отдельной ветке от M1-05 без изменения M1-06.
Фактический результат и проверки — `docs/m1-07-exact-units.md`.

Результат: длина хранится целым числом микрометров, время — микросекундами;
преобразования и округление явны. Pure calculator сохраняет исходные размеры,
поправки каждого конца и итог резки без binary float.

Проверки: EX-01 даёт 1031 мм провода и 950 мм оплётки; поправки −2/+3 хранятся
отдельно; позиции с разницей 1 мм не объединяются; дробная длина округляется вверх
до целого миллиметра по умолчанию, настраиваемый шаг применяется только к итогу.
Unknown/null отличается от физического нуля; незавершённая длина не даёт расход,
отрицательный итог и переполнение отклоняются. Геометрия и UI карты не входят.

## M1-08 — норматив времени и EX-02

Результат: pure calculator погонной и статичной операции с отдельными `Tmachine`,
`Tperson`, `Toperation=max(...)` и labour; коэффициенты повторения `q` и действия
инструмента `K` применяются один раз на своём уровне.

Проверки: для 20 мм EX-02 даёт `Tmachine=5,1 с`, `Tperson=7 с`, `Toperation=7 с`
и 700 человеко-секунд на 100 штук; статичная операция не принимает L; пусто и
ноль различаются; `q` и `K` не умножаются дважды. Чтение БД.ОП и планировщик не входят.

## M1-09 — два независимых рабочих места и EX-03

Результат: pure capacity calculator равномерно распределяет целые изделия по N
полным независимым комплектам; duration — максимум мест, labour — сумма.

Проверки: при 120 с подготовки на каждое из двух фактически занятых мест 11 изделий
→ 6/5, 480/420 с, блок 480 с, трудоёмкость 900 человеко-секунд; подготовка не
начисляется пустому месту; проверены одно место, мест больше изделий и недоступный комплект.
Граф, передаточные партии и очередь инвентарных номеров остаются M6.

## M1-10 — целостный backup

Статус: ядро backup, retention и policy primitives завершены. Автоматическое
подключение policy до миграции активного поколения перенесено в M1-12, где оно
может соблюсти обязательный порядок pre-update backup → candidate → switch.

Результат: согласованный снимок SQLite штатным backup API и всех immutable
content-addressed attachments, ссылки на которые читаются именно из снимка БД;
manifest с app/schema/revision и SHA-256 каждого файла; staging и атомарная публикация.
Внешний backup-root задаётся orchestration-кодом. Policy primitives при явном
вызове обнаруживают смену `lastRunAppVersion`, создают `pre-update` backup и
применяют retention с точным количеством. `RunTimerAsync` предоставляет первичную
проверку для catch-up и последующие регулярные проверки после своей активации.

Проверки: конкурентная смена ссылки не нарушает согласованность; копия проходит
integrity/hash; read-only root, ошибка или нехватка места не вызывают тихий fallback,
не публикуют backup и не удаляют предыдущий. Последняя успешная и pre-update копии
не удаляются; версия A→B при той же schema создаёт backup. `lastRunAppVersion`
обновляется только после успешной публикации, поэтому сбой повторяет попытку.
Автоматическое расписание и startup activation пока не подключены к `Program`.
Обязательный порядок `pre-update backup → candidate migration → CURRENT switch`
реализуется в M1-12; только после этого приложение сможет безопасно активировать
policy при запуске и догонять пропущенную регулярную проверку.

## M1-11 — восстановление backup

Статус: завершено. Фактический результат и проверки —
`docs/m1-11-storage-restore.md`.

Результат: команда проверки восстанавливает backup в новый recovery-root, повторно
проверяет DB/attachments/manifest и не меняет исходный `dataRoot`. Полное
восстановление — отдельная команда после явного подтверждения: сначала успешно
публикуется новый pre-restore backup текущего root; любая его ошибка отменяет
действие. Восстановленный candidate проверяется и только затем переключается.

Проверки: пробное восстановление читается и не меняет исходник; повреждение и
нехватка места не переключают root; полное восстановление без подтверждения
невозможно; обрыв до/после switch оставляет ровно одно валидное текущее поколение.

## M1-12 — безопасные миграции

Статус: завершено. Фактический результат и проверки —
`docs/m1-12-storage-migrations.md`.

Результат: перед N→N+1 успешно публикуется backup; его ошибка не позволяет начать
миграцию. Current generation копируется в candidate,
миграции выполняются транзакционно, затем проходят `integrity_check`, FK и доменная
проверка; только после этого атомарно меняется `CURRENT`.

Проверки: schema 1→2; отсутствующий шаг; исключение; crash points до, во время и
после crash-safe replace/write-through указателя `CURRENT`; старт выбирает ровно
одно полностью валидное поколение, recovery journal завершает/откатывает cleanup;
downgrade и необратимая in-place миграция запрещены.

## M1-13 — минимальный экспорт архива проекта

Статус: завершено. Фактический результат и проверки —
`docs/m1-13-project-export.md`.

Результат: расширяемый `.techmap-project.zip` с версионированным canonical manifest,
snapshot, жгутами, синтетическими pinned records и только referenced attachments; каждый
файл имеет SHA-256; экспорт выполняется staging → validate → atomic publish.

Проверки: проект с двумя жгутами экспортируется офлайн; лишний attachment не попадает;
локальные пути и секреты отсутствуют; ошибка не оставляет готовый архив. Полнота
компонентов/шаблонов/графики повторно проверяется после M2/M4. Это не XLSX/PDF/PNG
и не backup всей базы.

## M1-14 — импорт и восстановление проекта

Результат: до публикации проверяются format/version и конкретные лимиты числа файлов,
суммарного/распакованного размера, compression ratio, длины и duplicate/case-colliding
имён; запрещены traversal, symlink/reparse entries. Staging-копия проверяется и
мигрируется; новый project ID резервируется атомарно; project-owned ID remap сохраняет
ссылки и `restoredFrom`. Recovery journal связывает публикацию blobs и DB commit.

Проверки: повторный импорт создаёт ещё один ID/имя; два жгута и ссылки целы;
битый hash, zip bomb, traversal и несовместимая версия не создают видимый проект.
Crash после immutable blob до DB commit оставляет только безопасный orphan, который
recovery/GC удаляет; staging очищается; конкурентные импорты не занимают один ID.
Численные лимиты фиксируются до написания ZIP parser в этой карточке.

## M1-15 — сквозная приёмка M1

Результат: воспроизводимый win-x64 ZIP с автоматической проверкой своего manifest
при старте и сценарий: распаковать → создать проект/два жгута → restart → EX-01–03
→ экспорт → обновление schema с backup → импорт отдельной копии.

Проверки: произвольный путь, отсутствие .NET/Node/WebView2/интернета, сохранность
`dataRoot` при замене программы, блокировка второго процесса, прежние ID после
restart, пробное/полное восстановление, целый минимальный архив и бюджеты M0-05.
SHA-256 обнаруживает случайное повреждение, но не доказывает подлинность заменённых
manifest+binary. Физически чистый второй ПК и цифровая подпись остаются M9;
редактор, реальные базы, документы и LAN не входят.

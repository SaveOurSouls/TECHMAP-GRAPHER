# M1-05: вложения и закреплённые снимки

Статус: завершено 2026-09-12. Это рабочая запись реализации, не итоговое ТЗ и не
инструкция пользователя.

## Реализованный контракт

Бинарные вложения хранятся вне SQLite в `dataRoot/attachments`. Входной поток сначала
записывается в уникальный файл `staging`, одновременно считается SHA-256 и длина, затем
данные сбрасываются на диск и атомарно публикуются под именем хеша в каталоге
`blobs/<первые 2 символа>/<sha256>`. Два одинаковых файла дают один immutable blob;
конкурирующая публикация проверяет уже существующий файл. Имена хешей строго
канонические, reparse point для каталогов и blob отклоняется.

SQLite schema 3 хранит:

- метаданные blob `content_sha256`, `size_bytes`, `created_utc`;
- независимые ссылки проекта с собственным UUID, исходным именем, media type и purpose;
- закреплённые характеристики с собственным UUID, проектом, видом/ключом/версией
  источника, названием, значением, единицей, временем захвата и canonical JSON;
- SHA-256 canonical JSON для обнаружения повреждения снимка.

Публикация immutable blob выполняется до одной SQLite-транзакции метаданных и ссылки.
Поэтому исключение или остановка до commit не создаёт видимой ссылки проекта. После
атомарной публикации и до commit допустим безопасный unreferenced blob; его сборка с
периодом ожидания относится к будущему обслуживанию хранилища. Ссылочный blob никогда
не удаляется при откате, поскольку он может быть общим для нескольких проектов.

Закреплённый снимок нормализует Unicode в NFC и сохраняет значение как строку: точные
единицы и числовые преобразования входят в M1-07. Одинаковые проект, ключ, версия
источника и характеристика возвращают уже сохранённый снимок. Если источник повторно
использовал тот же version fingerprint для другого canonical payload, операция
отклоняется. Изменение mock-источника само по себе сохранённый проект не меняет.

Копирование проекта создаёт новые UUID ссылок и снимков, повторно использует immutable
blob и сохраняет canonical payload исходного снимка. Удаление проекта в будущем сможет
каскадно удалить ссылки, не удаляя общий blob без отдельной безопасной сборки мусора.

## Минимальный HTTP API

- `GET /api/v1/projects/{projectId}/attachments`;
- `POST /api/v1/projects/{projectId}/attachments`;
- `POST /api/v1/projects/{projectId}/attachments/{attachmentId}/validations`;
- `GET /api/v1/projects/{projectId}/attachments/{attachmentId}/content`.

Команда добавления принимает Base64 в JSON и ограничена 25 МиБ декодированных данных.
API наследует локальную session/Origin/CSRF/JSON-защиту M1-02. Это минимальная граница
для проверки хранения; пользовательский импорт файлов, thumbnails и обработка
изображений относятся к последующим редакторам.

## Проверки

Проверены потоковый SHA-256, дедупликация и конкурирующая публикация; очистка staging
при ошибке источника; обнаружение missing/length/hash corruption; отсутствие видимой
ссылки при ошибке до SQLite commit; сохранение ссылок и снимков после restart; повтор
версии, конфликт version fingerprint и копирование проекта; миграции schema 1→2→3 и
2→3; protected HTTP API и URL-префикс. Переносимый ZIP создаёт вложение, принудительно
останавливается, повторно открывает проект, проверяет UUID/SHA-256 и читает исходные
байты. Итог: frontend 24/24, .NET 168/168, регрессия M0 20/20; ZIP 45,53 МиБ
(106,88 МиБ распаковано), семь portable-режимов. Независимый review не оставил P1/P2.

В карточку не входят реальные справочники, XLSX/Google Sheets, обработка изображений,
UI выбора файла, команды/ревизии/autosave, backup, импорт/экспорт проекта и сборщик
неиспользуемых blob. Следующая карточка — M1-06.

# M1-15 — сквозная приёмка M1

Дата: 2026-09-12. Статус: принято автоматической приёмкой.

## Назначение и границы

Карточка закрывает этап M1 сквозным прогоном именно поставляемого win-x64 ZIP, а
не только отдельных библиотек из исходной рабочей копии. Проверяется цепочка от
старого принятого пакета M1-13 до текущего пакета M1-15: создание проекта с двумя
жгутами, перезапуск, экспорт, обновление хранилища, импорт независимой копии,
backup и оба вида восстановления.

Пакет M1-15 имеет версию `0.1.0-m1.15` и storage schema 6. В качестве исходной
версии обновления использован сохранённый настоящий пакет `0.1.0-m1.13` со
storage schema 4. Оба пакета сначала проходят проверку собственных manifest и
контрольных сумм.

## Фактический результат

Полный прогон завершён успешно со следующими результатами:

| Проверка | Результат |
|---|---:|
| Release-сборка и `build-package.ps1` | успешно |
| Все тесты .NET | 372/372 |
| Тесты frontend | 44/44 |
| Расчётные эталоны EX-01–03 | 4/4 |
| Режимы portable-пакета | 7 |
| Размер ZIP | 45,71 MiB |
| Размер распакованного пакета | 107,39 MiB |
| Обновление storage schema | 4 → 6 |
| Обязательный `pre-update` backup | 1 |

Размеры находятся внутри принятых бюджетов M0-05: не более 75 MiB для ZIP и не
более 200 MiB после распаковки. Пакет распаковывался и запускался из пути с
пробелами и кириллицей. Self-contained поставка не требует установленного .NET,
Node.js или WebView2 и не обращается к внешней сети для работы интерфейса.

Portable smoke текущей версии создал проект-контейнер и два независимых жгута с
количествами 5 и 12. Для каждого жгута сохранены собственные рабочие области Э4,
чертежа и маршрута. После перезапуска сохранены project ID, revision, порядок и
ID жгутов, их количества и ID всех шести документов. Отдельный сценарий обновления
создал прежней версией проект с двумя жгутами и общим legacy-количеством 20;
schema 6 перенесла его в каждый существующий жгут. Экспорт этого проекта и
последующий импорт текущей версией создали отдельный проект с новыми
project-owned ID; исходный и импортированный проекты содержат по два жгута и не
изменяют друг друга.

Обновление существующего `dataRoot` выполнило миграцию schema 4 → 6. До
переключения поколения опубликован и проверен ровно один обязательный backup
вида `pre-update`, сохранивший исходную schema 4. Замена папки программы не
изменила внешний каталог данных.

## Backup и восстановление поставляемым EXE

В portable EXE проверены четыре offline-команды обслуживания. Обычный backup:

```powershell
.\Techmap.Server.exe `
  --data-root="C:\TECHMAP\data" `
  --create-backup `
  --backup-root="D:\TECHMAP-backups"
```

Пробное восстановление в новый каталог без изменения рабочего `dataRoot`:

```powershell
.\Techmap.Server.exe `
  --data-root="C:\TECHMAP\data" `
  --dry-run-restore="D:\TECHMAP-backups\backup-..." `
  --recovery-root="C:\TECHMAP\restore-check"
```

Полное восстановление состоит из двух явно разделённых запусков. Сначала
создаётся новый plan-файл вне `dataRoot`:

```powershell
.\Techmap.Server.exe `
  --data-root="C:\TECHMAP\data" `
  --prepare-full-restore="D:\TECHMAP-backups\backup-..." `
  --restore-plan="C:\TECHMAP\restore-plan.json"
```

Команда сохраняет одноразовый `PlanId` и fingerprint в plan-файле, а в stdout
печатает путь плана и точную строку подтверждения. Пользователь отдельно помещает
эту строку в файл, после чего выполняется восстановление:

```powershell
.\Techmap.Server.exe `
  --data-root="C:\TECHMAP\data" `
  --execute-full-restore="C:\TECHMAP\restore-plan.json" `
  --confirmation-file="C:\TECHMAP\restore-confirmation.txt" `
  --pre-restore-backup-root="D:\TECHMAP-pre-restore"
```

Для автоматизации предусмотрены стабильные stdout-маркеры статуса, ID, путей,
SHA-256 и восстановленного поколения с префиксом `TECHMAP_STORAGE_`. Ошибки дают
ненулевой код выхода, не печатают ложный success marker и при
`--no-error-dialog` не создают системное диалоговое окно.

Сквозной тест подтвердил, что dry-run создаёт отдельный читаемый recovery-root и
не меняет рабочее хранилище. Полное восстановление сначала публикует ровно один
проверенный `pre-restore` backup, затем атомарно переключает поколение и возвращает
оба проекта с прежними ID, revision, жгутами и документами. Неверная строка
подтверждения не меняет `CURRENT` и SHA-256 рабочей БД.

## Ошибочные случаи

Приёмка отдельно проверила следующие отказы:

- занятый `dataRoot`: offline-команда не подключается к уже работающему web-хосту
  и завершается ошибкой;
- неверное подтверждение полного восстановления: план не выполняется, рабочая БД
  остаётся неизменной;
- повреждение ZIP без изменения его размера: package manifest обнаруживает
  несовпадение контрольной суммы до запуска приложения;
- повреждённый backup или несогласованное содержимое: компонентные restore-тесты
  подтверждают отказ до публикации рабочего поколения;
- повторный запуск после остановки владельца и разные представления одного
  каталога сохраняют правило одного writer; независимые `dataRoot` работают
  одновременно.

Основной M1-15 сценарий ограничивает ожидание запущенных им процессов и HTTP-запросов,
а его артефакты создаются только в уникальном каталоге
`artifacts/m1-15/r-<id>` с owner marker.

## Воспроизведение

Основной сквозной сценарий:

```powershell
.\scripts\test-m1-15.ps1
```

Он использует локальный checkpoint настоящего ZIP M1-13 с закреплённым SHA-256,
собирает текущий ZIP, запускает
расчётные тесты, portable-проверки, обновление, экспорт/импорт и восстановление.
Для нового внешнего checkpoint требуется передать одновременно путь и ожидаемый
SHA-256; это не позволяет молча заменить принятую предыдущую сборку.

Проверки компонентов выполняются отдельно командами `dotnet test` и frontend
test/build, а пакет создаётся `scripts/build-package.ps1 -Configuration Release`.

## Ограничения результата

M1 подтверждает каркас данных, переносимость, обновление и восстановление. В него
не входят предметный графический редактор, реальные каталоги M2, Э4 и расчёт
полного жгута, производственные документы, LAN и совместная работа.

Проверка контрольных сумм обнаруживает случайное повреждение, но не доказывает
подлинность, если злоумышленник одновременно заменил файл и manifest. Цифровая
подпись и испытание на физически чистом втором компьютере остаются задачами M9.
Полное восстановление является offline-операцией, требует свободного `dataRoot`,
нового plan-файла вне него и точного отдельного подтверждения. Проверочные
артефакты и приватные данные источников не предназначены для Git.

# Координация чатов и сборщика

Этот каталог описывает, как вести несколько чатов Codex над одним проектом и как передавать готовые изменения чату-сборщику. Рядом с checkout могут находиться другие worktree и архивные снимки. Правила проекта из [`AGENTS.md`](../../AGENTS.md), [`docs/project-workflow.md`](../project-workflow.md) и карточек задач имеют приоритет.

## Основная модель

У каждой самостоятельной задачи есть один рабочий чат, одна ветка/worktree и один владелец файлов. Чат-сборщик не ищет изменения по каталогам и не копирует файлы вручную: он получает точные хеши проверенных коммитов и применяет их к своей интеграционной ветке.

```text
чат задачи -> ветка/worktree -> проверенный коммит -> handoff
                                                     |
                                                     v
                                        чат-сборщик / ветка интеграции
                                                     |
                                                     v
                                      общие проверки и итоговый коммит
```

## Роли

### Чат задачи

1. Перед началом читает `AGENTS.md`, `docs/project-workflow.md`, `status.md`, связанную карточку и Git-состояние.
2. Фиксирует границы задачи и список файлов, которыми владеет. Общие файлы (`AGENTS.md`, `README.md`, `status.md`, индекс задач и упаковочные скрипты) меняет только назначенный оркестратор.
3. Реализует только свою карточку, запускает обязательные проверки и создаёт содержательный коммит.
4. Передаёт сборщику handoff по шаблону [`agent-handoff.md`](agent-handoff.md). Незакоммиченные изменения в интеграцию не передаются.

### Чат-сборщик

1. Работает в отдельной ветке интеграции (например, `codex/integration`) и не редактирует worktree чатов задач.
2. В начале каждого цикла просматривает `git worktree list`, `git log --all --oneline --decorate` и [`integration-log.md`](integration-log.md). Если исходный коммит находится только в origin, выполняет `git fetch --all --prune`.
3. Проверяет, что каждый заявленный коммит существует (`git show --stat <hash>`), и применяет его через `git cherry-pick` либо согласованный merge.
4. Разрешает конфликты только после сверки владельцев файлов и требований карточек. Не затирает незавершённые изменения другого чата.
5. После каждой группы связанных коммитов запускает обязательные проверки. `git cherry-pick` сам создаёт интеграционный коммит; отдельный коммит нужен для разрешения конфликта, документации или других новых изменений. Обновляет `status.md`/индекс задач по правилам проекта.
6. Записывает результат в журнал: исходные хеши, итоговый хеш, проверки, конфликты и ограничения.

## Правило передачи

Сообщение сборщику должно содержать все поля из [`agent-handoff.md`](agent-handoff.md): идентификатор карточки, ветку/worktree, коммит(ы), изменённые файлы, проверки, зависимости и ограничения. Формулировки «готово» или ссылка только на название чата недостаточны.

Если коммит не находится в checkout сборщика, сначала ищите его среди локальных веток и worktree; затем обновляйте удалённые ссылки:

```powershell
git log --all --oneline --decorate --grep="<часть сообщения>"
git show <hash>
git worktree list
git fetch --all --prune
git show <hash>
```

Если после `fetch` хеш отсутствует, исходный чат должен указать правильный remote/ветку или завершить коммит в том же репозитории. Сборщик не переносит файлы из соседнего каталога и не считает незакоммиченный worktree результатом.

## Жизненный цикл

Карточка сохраняет статусы из [`docs/project-workflow.md`](../project-workflow.md): `backlog -> ready -> in-progress -> ready-for-review -> accepted`. Запись `integrated` ведётся отдельно в журнале интеграции.

`ready-for-review` означает, что чат задачи проверил и закоммитил свою ветку. `integrated` означает, что сборщик применил этот хеш и прошёл интеграционные проверки. `accepted` означает ручную приёмку владельца проекта; она не выводится автоматически из зелёных тестов.

## Где смотреть состояние

- `docs/coordination/chat-registry.md` — роли, Thread ID и текущий снимок чатов.
- `docs/coordination/integration-log.md` — реестр переданных и интегрированных коммитов.
- `docs/coordination/agent-handoff.md` — копируемый формат сообщения от чата задачи.
- `tasks/README.md` и карточка задачи — требования, владельцы файлов и критерии.
- `status.md` — последний проверенный срез активного проекта.

Корневые архивы, ZIP и каталоги с суффиксами `_build`/`_push` не являются источником истины для интеграции. Источник истины — Git-объекты выбранного репозитория и зафиксированные в журнале хеши.

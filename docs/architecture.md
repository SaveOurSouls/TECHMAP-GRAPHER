# Восстановленная архитектура

## Границы системы

TECHMAP-GRAPHER — локальное Windows web-приложение. Запускаемый сервер и статический React-клиент поставляются одним self-contained win-x64 архивом, а рабочий data-root находится отдельно. Экспорт проекта — отдельный переносимый архив.

## Слои и зависимости

```text
Browser / React + TypeScript (src/Techmap.Client)
                 │ HTTP JSON / binary attachments
ASP.NET Core Web (src/Techmap.Web)
                 │ contracts + application ports
Application services (src/Techmap.Application)
                 │ domain rules / repositories
Domain model (src/Techmap.Domain)
                 │ SQLite adapters, CAS, import/export
Infrastructure.Sqlite + Infrastructure.GoogleSheets
```

- `Techmap.Contracts` содержит DTO, ошибки, версии API и runtime-конфигурацию.
- `Techmap.Domain` содержит идентичности проектов/жгутов и инварианты предметной области.
- `Techmap.Application` задаёт границы хранения и операции над проектами, справочниками, шаблонами, маршрутами и картой резки.
- `Techmap.Infrastructure.Sqlite` реализует поколенческое SQLite-хранилище, backup/restore, импорт/экспорт, вложения и snapshots.
- `Techmap.Web` связывает DI, security middleware, startup maintenance и endpoint-модули.
- `Techmap.Client` хранит редакторскую модель, команды, физическую топологию, связанные виды и manufacturing workspace.

Границы подтверждены регистрацией сервисов в `src/Techmap.Web/Program.cs`, endpoint-модулями и интерфейсами Application. **Источник: найдено в коде**.

## Запуск и владение data-root

1. `Program.cs` читает `ServerOptions`: порт, path base, data-root, backup-root и offline-команды.
2. Для обычного запуска `DataRootLease.Acquire` создаёт эксклюзивное владение. `LocalInstanceRecord` публикует сведения о владельце; при конфликте `BrowserLauncher` переиспользует доступный экземпляр.
3. `DataRootLayout.Initialize` создаёт маркер формата и каталоги. Затем выполняются миграция, pre-update backup и проверка schema version.
4. SQLite открывается через `SqliteStorage`; регистрируются stores/services и hosted backup policy.
5. Kestrel слушает loopback. Middleware проверяет точный loopback authority, path base, session и mutation cookie.
6. После регистрации API и static files браузер получает runtime-config с app/API/schema версиями.

Это последовательность фактического старта в `Program.cs`, `ServerOptions.cs`, `DataRootLayout.cs`, `LocalInstanceRecord.cs`. **Источник: найдено в коде**.

## Данные и транзакции

SQLite разбит на поколения; указатель current generation и миграционный сервис позволяют подготовить новую схему до переключения. Backup policy делает резервную копию до обновления и фиксирует успешный запуск. Проектные вложения хранятся content-addressed, а каталог и шаблоны используют version/snapshot records. Ревизия проекта и expected revision защищают сохранение от тихого перезаписывания.

Полный backup/restore выполняется отдельными offline-командами с dry-run, планом, pre-restore backup и явным confirmation file. Проектный import/export не является копированием всего data-root. **Источник: найдено в коде** (`SqliteStorage*`, `Program.cs`, `ServerOptions.cs`, `ProjectExport/ImportService`).

## Общая модель редактора

`HarnessDesignDocument` является общим документом жгута. В нём присутствуют соединители/контакты, провода/кабели, маршруты Э4 и чертежа, слои, физическая топология, размеры, оболочки, узлы, diff-pair и screens. `EditorCommand` — единственный типизированный вход для изменений; `applyEditorCommand` после команды выполняет нормализацию физической топологии, автоматическую маршрутизацию и сверку размеров/документов.

`drawingDocuments.graphics` хранит графические фигуры рисунка с явным видом `drawing` или `e4`. Общая сцена фильтрует их по виду; команда `set-drawing-documents` проводит изменения через историю редактора. Эти фигуры не становятся электрическими узлами и не добавляют материалы в спецификацию. Клиентский `validateDrawingDocuments` и серверный `HarnessDrawingDocumentsValidator` проверяют их формат. Контракт описан в [ADR-0013](decisions/0013-shared-graphics-and-route-semi-finished-copy.md).

Для Э4 `views.e4.e4RoutingMode` хранит переключатель ортогональной или угловой
автоматической трассировки. Дифференциальные X-мотивы вычисляются по тем же
маршрутам `WireInstance.e4Route`; автоматическое перестроение при необходимости
сближает фактические параллельные сегменты до шага строки, поэтому графика не
становится независимой копией проводов. **Источник: найдено в коде**
(`model.ts`, `commands.ts`, `e4-router.ts`, `CanvasViewport.tsx`); критерии
владельца зафиксированы в [REQ-045](requirements.md).

Физический граф (nodes, segments, joining pipes, coverings) не смешивается с электрическими endpoint/junction связями. Представления ссылаются на стабильные ID; координаты и масштаб могут отличаться между Э4 и чертежом. **Источник: найдено в коде** (`model.ts`, `commands.ts`, `physical-topology-*`, `drawing-*`).

### Прозрачность П и ОП (REQ-027)

`drawingDocuments.pipeOpacity` — единое значение прозрачности П и ОП от 0 до 1. Левая панель чертежа сохраняет его через `set-drawing-documents`; свойства отдельных трубок локальный ползунок не показывают. Старые `PhysicalSegment.opacity` и `PhysicalJoiningPipe.opacity` принимаются при загрузке для совместимости. `physicalTopologyScene` передаёт итог в `EditorSceneObject.metadata`, а `CanvasViewport` применяет его только при рисовании.
Подробные критерии и проверка: [карточка 013](../tasks/013-pipe-opacity.md).

### Общие выходы ОП (REQ-056–058)

`PhysicalJoiningPipe` хранит две длины прямого выхода (`enterLength` и
`exitLength`). Сцена создаёт по одной управляющей ручке на каждый торец ОП;
`joiningPipeExitVector` вычисляет направление по первому отличающемуся участку
оси и используется одинаково в сцене, команде и проекции входящих П. Переходные
изгибы членов остаются отдельными авторскими данными, а расчётные станции не
материализуются в путь при перемещении. Старые ОП без длин используют
детерминированный запасной размер до первого сохранения. Команды проходят
обычную нормализацию физической топологии и не меняют электрические ID или
производственные длины. Проверки и ограничения описаны в [карточке 031](../tasks/031-op-shared-exits-and-stable-drag.md).

### Срединные ручки П (REQ-057–058)

`physical-scene.ts` размещает срединные ручки по видимой скруглённой трассе и
передаёт соответствие исходному участку в `midpointSources`. Расчётные станции
общего выхода ОП отделены от авторских перегибов. Ручка, совпадающая с доступным
перегибом, не должна предлагать второй неоднозначный захват.

`physical-route-point-command.ts` преобразует выбранную ручку в команду относительно
документа начала жеста. `HarnessDesignEditor` использует этот путь и для
предпросмотра, и при отпускании указателя: индекс вставки не пересчитывается по
новому положению мыши.

`JoiningPipeMember.authoredBendRegions` связывает авторский перегиб с сегментом,
индексом и участком ОП, а `displayPoint` сохраняет его видимые координаты.
При редактировании старого документа данные заполняются по прежней сцене.
Проекция документа с этими данными строится по упорядоченным авторским и
управляемым ОП точкам; исходные расчётные станции не добавляют скрытых колен.
Клиентская и серверная валидация проверяют одинаковые ограничения ссылок,
индексов и координат. Решение описано в
[ADR-0011](decisions/0011-op-authored-bend-ownership.md).

Ctrl для П в составе ОП выбирает ближайшую допустимую опору своего внешнего
плеча. Направляющая показывает выбранную опору, а перенос соседних точек
останавливается у границы участка ОП. Проверки и границы визуальной приёмки — в
[карточке 032](../tasks/032-op-midpoint-video-regression.md).

## Manufacturing и связанные виды

Manufacturing route-модули получают источники из сохранённого design document, строят строки маршрута и выполняют readiness/rebase проверки. Операции, терминалы, материалы и фотографии являются ссылками или вложениями проекта, а не независимыми копиями исходных физических объектов. Cut-list endpoint повторно проверяет readiness на сервере. **Источник: найдено в коде** (`manufacturing/*`, `HarnessCutListEndpoints.cs`).

### Рисунки полуфабрикатов провода (REQ-051/060/061)

`WireBlankCatalogSeed` создаёт 13 стартовых записей `technology-wire-blanks` по `manifest.json` только при отсутствии активной версии; существующие пользовательские записи и закреплённые snapshots не перезаписываются. `WireBlankCatalogEditor` и маршрут используют общий `wire-blank-artwork.mjs`: тело, выбранные независимо концы и цвет изоляции собираются в SVG для показа. `photoDataUrl` имеет приоритет над типовым рисунком. Генератор `design/route-wire-illustrations/generate.mjs` выпускает из того же исходника 13 полных SVG и 7 отдельных частей; `verify.mjs` сверяет их с манифестом. **Источник: найдено в коде** (`WireBlankCatalogEditor.tsx`, `wire-blank-artwork.mjs`, `WireBlankCatalogSeed.cs`, `route-wire-blank.ts`); проверки и передача сборщику — в [карточке 037](../tasks/037-wire-catalog-artwork-refresh.md).

В `RouteWorkspace` открытая карта периодически читает последнюю сохранённую
ревизию, перебазирует не удалённые источники и сериализует сохранение. Исчезнувшие
ссылки требуют подтверждения; длины отображаются из чертежа, а собственные
поля строки сохраняются в маршруте. Этот механизм описан в
[ADR-0008](decisions/0008-route-source-synchronization.md); двухоконная и ручная
приёмка вынесены в [задачу 008](../tasks/008-route-live-source-sync.md).

## Recovery и отказоустойчивость

Recovery-журнал расположен в data-root вне экспортируемого проекта. `HarnessDesignRecoveryEndpoints` даёт GET/PUT/DELETE по project/harness/draft ID; журнал ограничивает размер 16 MiB и защищает sequence conflict. Клиент после успешного сохранения удаляет только архивы, созданные текущим restore flow (исправление `2ba1562`). **Источник: найдено в коде**.

## Поставка

`scripts/build-package.ps1` публикует клиент, сервер и `PACKAGE-MANIFEST.json`; сервер в packaged build проверяет манифест до запуска. Текущий зафиксированный пакет описан в `docs/m5-07-acceptance.md`; ZIP и `artifacts/` намеренно не входят в Git. **Источник: найдено в коде** (скрипты и acceptance protocol).

## Наблюдаемые ограничения

- В текущей среде прямой portable-запуск из пути с кириллицей иногда получает `UnauthorizedAccessException`; тот же архив проходит через ASCII drive alias. Это ограничение среды проверки, а не доказанный дефект приложения. **Источник: найдено в коде** (протокол portable-проверки).
- Автоматические тесты не заменяют ручную визуальную приёмку маршрута и сложных UI-сцен. **Источник: предположение**, основанное на явно отмеченном ограничении acceptance.

## Рисунок сборки: полный редактор копии (REQ-062)

`RouteAssemblyDrawing` монтирует `HarnessDesignEditor.localCopy` с полной независимой моделью без `manufacturingRoute`. Команды изгибов, привязок, размеров и оформления общие с основным редактором. Локальные Save/Cancel не обращаются к design/recovery/placement mutation API. `presentation.drawingCopy` хранит документ и hidden IDs; rebase обновляет производственные источники отдельно. Превью строится из копии общим рендерером с её слоями, цветами и текстурами.

Тот же локальный редактор доступен строке `semiFinished`: её рисунок сохраняется в `presentation.drawingCopy`, а закреплённый рисунок провода продолжает показываться отдельно. Состав, операции, `wireBlankSelections` и производственные длины не вычисляются из копии. Сервер и клиент валидируют копию для обоих видов строк маршрута.

Клиентский `route-drawing-copy` и серверный `ManufacturingRouteValidator` проверяют копию (1 MiB, ограниченная сложность, запрет рекурсивного маршрута). Общий документ и recovery допускают 16 MiB; SQLite v23 мигрирует CHECK таблицы. Закреплённые project snapshots сохраняют приоритет, недостающие рисунки новых локальных соединителей читаются из опубликованных версий библиотеки. Ограничения переноса и legacy migration: [ADR-0012](decisions/0012-route-full-drawing-copy.md), [карточка 038](../tasks/038-route-full-drawing-editor.md). **Источник: найдено в коде.**

### Тестовые режимы Маршрут v2 и UML (REQ-092/093/094)

Клиентские `manufacturing-v2/` и `uml/` добавляют две отдельные кнопки и не расширяют серверный контракт `HarnessDesignDocument`. V2 строит начальные карточки через `buildRouteSourceItems`, хранит визуальные узлы и направленные связи по устойчивым ID в локальном кеше браузера и не содержит операций/расчёта времени. Из свойств выбранной карточки V2 открывается существующий `RouteAssemblyDrawing`: исходная и изолированная копии рисунка сохраняются на узле графа V2, а исходный чертёж и старый маршрут не изменяются. UML хранит независимый DAG, умеет импортировать V2 и считает погонные и статичные операции на клиенте; импорт не передаёт рисунки. Это временная тестовая граница до согласования отдельного серверного endpoint/store.

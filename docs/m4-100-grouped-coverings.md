# М4-100 — общая оболочка нескольких пайпов

Статус: реализация начата, пользовательский сценарий ещё не готов.

Требования: ПКМ по оболочке → «Объединить» → выбрать пайпы/существующие группы
с подсветкой и кратким составом → сохранить. Общая оболочка перемещается вдоль
собранных пайпов. Плоская укладка размещает их рядом, объёмная — как проекцию
упакованных поперечных сечений. Общая оболочка не меняет электрические связи.

Порядок реализации:

1. Вычислитель поперечного сечения, ID и размеры независимо от Canvas.
2. Сохранённый состав группы, ссылки на пайпы/группы; защита от циклов,
   повторного включения одного пайпа, отсутствующих участников. Сервер и клиент.
3. Контекстное действие, режим выбора, краткий состав/подсветка, сохранение.
4. Раскладка пайпов и их проводов под общим контуром, перенос общей оболочки;
   спецификация без дублирования материалов, удаление/разделение участников.
5. API, браузер, повторное открытие и ZIP; аудит по исходному ТЗ.

## Первый исходный срез

`pipe-bundle-packing.ts` — чистый вычислитель плоской/объёмной укладки.
Плоский режим сохраняет порядок и даёт ширину, равную сумме диаметров.
Объёмный использует детерминированные касания окружностей и размещает крупные
сечения первыми; выход сохраняет порядок/ID и содержит смещение/глубину.
Это допустимая компактная укладка, не доказанный глобальный оптимум.

Девять новых тестов: точный плоский ряд, три касающихся одинаковых круга,
1/2/8/32 смешанных сечения без пересечений, границы общего контура,
детерминизм/неизменность входа, масштаб 0,001/1000, некорректные размеры/ID.
1180 клиентских тестов и TypeScript прошли. UI, API и пакет не менялись:
модуль пока не подключён. Последний пользовательский ZIP — М4-99-r7.

## Сохранённый состав и границы валидации

Оболочка может хранить `bundle: { mode: "flat" | "round", members }`.
Участник — `{ kind: "segment" | "covering", id }`. Вложенная ссылка ведёт
только на другую группу, обычные покрытия остаются слоями своего пайпа.
`spans` задают продольную опору оболочки и должны ссылаться на её участников.
Порядок групп в массиве покрытий не влияет на проверку состава.

Клиент и сервер отвергают циклы, отсутствующие ссылки, повторные листья через
разные ветви, неподходящую опору, некорректный режим/тип участника. Пределы:
128 листьев и 16 уровней. Ограничение глубины действует и для уже вычисленной
подгруппы. Старые покрытия без `bundle` проходят прежнюю валидацию.

Проверено: 1197 клиентских тестов, TypeScript/build, 875 .NET Release-тестов,
self-contained publish и API на `.build/m4-100-model-host` с синтетическими
данными `artifacts/channels-smoke/test-6rPjA5`. Состав сохранился через JSON,
Undo, перезапуск EXE, копирование и экспорт/импорт. Прямой API-запрос с циклом
вернул 400 и не изменил сохранённый документ.

Это исходный срез формата, не пользовательский выпуск. Изолированный хост
содержит новую модель поверх файлов r7, ZIP для него не создавался. Нельзя
считать модель завершённым объединением: UI и renderer ещё не используют
состав, удаление/разделение участников требует следующего слоя. При разрезе
пайпа его последовательные части не должны становиться параллельными кругами
поперечного сечения — это отдельный инвариант следующего этапа.

## Изменения топологии и продолжения участников

У участника `kind: "segment"` добавлены необязательные `continuationIds`.
Это последовательные части одного поперечного сечения: разрез вставляет новый
ID после разрезанной части, не добавляя ещё один параллельный участник группы.
Вложенные группы сохраняют свои ссылки; их продольные spans делятся как раньше.
Клиент и сервер проверяют непрерывность from/to, отсутствие возвратов, повторов
и отсутствующих ID. Общий предел 128 листьев учитывает также продолжения.

Удаление пайпа/соединителя очищает группы изнутри наружу. Оставшаяся единственная
часть становится обычной оболочкой; родитель получает её сохранившийся состав.
Если пропал участок посередине продольного участника, оставшиеся несвязные части
исключаются из группы, но сами пайпы остаются в документе. Оболочка без опоры
удаляется. Удаление вложенной оболочки очищает ссылки родителей. Все изменения
проходят одной командой и отменяются вместе. Подсветка группы учитывает провода
всех участников и продолжений, а не только опорный span.

Проверено 25.09.2026: 1204 клиентских теста, TypeScript, production build,
883 .NET Release-теста, self-contained publish. API тестового EXE
`.build/m4-100-topology-host`: сохранение продольного участника через перезапуск,
копирование и экспорт/импорт; цикл и разорванный путь возвращают 400 без изменения
документа. Данные проверки: `artifacts/channels-smoke/test-4wHzQt`.
Пользовательские проекты не открывались. Для запуска EXE потребовался доступ
вне sandbox к Windows ACL каталога регистрации локальных экземпляров.

Инструменты клиента запускались напрямую из установленных node_modules:
pnpm текущей среды пытался переустановить зависимости. Publish использовал
временный lock-файл в obj для ILLink и NuGetAudit=false; зависимые пакеты взяты
из локального кэша, исходные lock-файлы не изменены. Нового пользовательского
ZIP нет: UI выбора и геометрическая укладка ещё не подключены. Цель активна.

## Выбор состава и вычисление вложенных сечений

Добавлен UI: ПКМ по оболочке → «Объединить», панель состава в верхней плашке,
выбор пайпов/готовых групп кликом на поле или в списке, отдельная подсветка,
плоский/объёмный режим. Черновик не меняет документ до «Сохранить»; вся операция
отменяется одним Undo. Циклы, повторные листья и потеря опорного пайпа блокируют
сохранение. Escape/«Отмена» закрывают выбор; клики, двойной клик и Delete во время
выбора не изменяют геометрию. При начале выбора контекстное окно закрывается.

`pipe-bundle-section.ts` вычисляет сечения вложенных групп: последовательные
продолжения используют один диск, вложенная группа — свой охватывающий диаметр,
обычные покрытия участников входят в размер. Расчёт даёт смещение и глубину
каждого листа; ширина передана общей оболочке. Это ещё НЕ готовая пространственная
укладка: сами пайпы и провода пока идут по прежним экранным траекториям.

Проверки: 1211 клиентских тестов, TypeScript и production build. Браузерный
синтетический стенд `.build/m4100-smoke.html` использует реальные CanvasViewport,
DrawingObjectProperties, PipeBundleEditor и команды: ПКМ → выбор второго пайпа
на поле → сохранение → один Undo выполнены. Полный редактор с API этим стендом
не покрыт; сервер не менялся (883 теста и API проверены в предыдущем срезе).

Следующий обязательный слой: проекция пайпов, проводов и нижних покрытий вдоль
общей опоры; переходы у границ, вложенность и перенос оболочки. Нельзя подменять
это копией одинаковой оболочки на каждый пайп или одним расширением ширины.
Затем полный редактор/браузер, API и новый ZIP. Последний пользовательский ZIP r7.

## Проекция участников — исходный срез

`pipe-bundle-projection.ts` сводит пайпы на общий опорный маршрут в пределах
оболочки. Переходы начинаются до её краёв, концевые узлы остаются на месте.
Станции добавляются и для прямых пайпов без перегибов. Продолжения используют
единый продольный параметр; узел разреза и его ветвь следуют той же проекции.
Вложенные оболочки используют центр своей группы и рисуются изнутри наружу.
Провода используют проекцию пайпа; длины, электрические концы и авторские пути
не переписываются. Экранные станции не становятся редактируемыми перегибами.

Проверено: 1220 клиентских тестов, TypeScript, production build. Девять новых
сценариев проверяют прямые пайпы, провод внутри пайпа, перенос покрытия и JSON,
продолжения/узел/ветвь, вложенность, обратное направление, координаты ручек и
неизменность исходных данных. Браузерный синтетический Canvas-стенд: плоское
объединение двух пайпов, объёмное трёх, сохранение и один Undo. Визуально видны
схождение и расхождение пайпов под одним контуром. Пользовательские данные не
использовались.

Ограничения среза: перетаскивание оболочки через несколько последовательных
spans пока изменяет только выбранный span; контекстное присоединение новой
ветви на смещённой проекции ещё требует обратного преобразования координат.
Для вложенных/перекрывающихся групп нужны дополнительные сквозные сценарии
редактирования. API/publish/полный редактор/ZIP в этом срезе не повторялись.
М4-100 не закрыт; исходный срез не объявляется пользовательским выпуском.

## Перенос через разрез и контекстные координаты

`covering-motion.ts` переводит части опоры в единый продольный параметр:
перенос тела сохраняет длину всех покрытых интервалов, а растяжение внешнего
края может перейти через узел на соседнее продолжение. Spans заново нарезаются
по существующим ID; внутренняя граница не становится ручкой или поперечным
контуром оболочки. При достижении конца опоры ограничивается весь интервал.
Неизменный жест возвращает исходную оболочку. Производственная ручная длина
не пересчитывается из координат.

Контекстные операции в полном редакторе используют обратную проекцию:
координата на отображаемом пайпе преобразуется в соответствующую станцию
авторского пути. Это применяется к Т-ветвлению, покрытию и подключению узла.
Регрессии подтверждают положение нового узла/ветви после повторной проекции.

Проверено 25.09.2026: 1225 клиентских тестов, TypeScript/build, 883 .NET
Release-теста, self-contained publish `.build/m4-100-motion-publish`.
Браузерный синтетический стенд на порту 5180: группа → разрез → перенос
оболочки на 60 единиц → spans .4/1 + 0/.6 стали .6/1 + 0/.8 → один Undo.
Внутреннего шва и ручек нет; оба входа следуют переносу.

API `.build/m4-100-motion-host`, данные `artifacts/channels-smoke/test-DTr4Xf`:
движение последовательной оболочки, сохранение геометрии после restart,
copy, export/import, неизменность документа после отклонения цикла/разрыва.
Тест обновляет документ иммутабельно, как команды редактора; мутация ранее
закэшированного объекта исправлена в самом smoke. Sandbox-запуск EXE был
отклонён Windows ACL регистрации локального экземпляра; повтор вне sandbox
успешен. Пользовательские проекты не использовались.

Полный редактор с API в браузере, ZIP и итоговый аудит М4-100 ещё впереди.
Перенос оболочки с несколькими независимыми продольными опорами пока применяется
к выбранной опоре; требуется отдельный сценарий синхронного перемещения таких
покрытий. Обычная оболочка одной непрерывной группы проверена.

## М4-100-r1 — согласованные края, приёмка объединения

Версия `0.56.1-m4-100-r1`. Две новые регрессии воспроизвели отказ синхронного
изменения края: ранее изменялась только выбранная опора. Теперь редактируется
соответствующий край всех опор, с общим нормированным смещением и ограничением
первой достигнутой границы. Обратное направление меняет from/to местами.
Разрезы перераспределяются, раздельные интервалы сопоставляются по порядку
вдоль общей оси. Неизменные привязки противоположных краёв сохраняются.
Ручная длина и электрические данные не меняются. Подсветка старой ручки
сбрасывается при начале жеста и больше не остаётся на прежнем месте.

# M1-14 — безопасный offline-импорт проекта

Дата: 2026-09-12. Статус: реализовано.

## Назначение и границы

Импорт принимает архив `.techmap-project.zip` формата M1-13 и создаёт в выбранном
`dataRoot` новый независимый проект. Исходный проект, архив и другие проекты не
изменяются. Это перенос предметного snapshot одного проекта, а не восстановление
всего хранилища и не слияние изменений с уже существующим проектом.

Импортируются проект, жгуты, ссылки на вложения, referenced content-addressed
blobs и закреплённые характеристики. Журнал команд и версии исходного проекта не
переносятся: новая копия публикуется с `revision = 0` и пустой историей команд.

## Offline CLI

Импорт запускается отдельным режимом сервера:

```powershell
.\Techmap.Server.exe `
  --data-root="C:\TECHMAP\data" `
  --import-project="C:\Exchange\project.techmap-project.zip"
```

Архив должен существовать, иметь расширение `.techmap-project.zip`, находиться
вне `dataRoot` и не проходить через reparse point. Режим требует эксклюзивной
lease каталога данных, несовместим с `--export-project` и `--verify-package`, не
запускает Kestrel и браузер. Аргумент импорта также подавляет системное GUI-окно
ошибки; причина остаётся в stderr, startup-журнале и коде выхода.

При успехе CLI выводит:

```text
TECHMAP_PROJECT_IMPORT_STATUS=ok
TECHMAP_PROJECT_IMPORT_PROJECT_ID=<новый UUID>
TECHMAP_PROJECT_IMPORT_INCREMENT=<новый порядковый номер>
TECHMAP_PROJECT_IMPORT_SHA256=<sha256 исходного zip-архива>
```

## Независимость, ID и имя

Для каждой новой операции создаётся новый project ID. Все project-owned ID
жгутов, ссылок на вложения и закреплённых характеристик детерминированно
переназначаются внутри операции, поэтому внутренние ссылки остаются целыми, но не
совпадают с ID исходника. CAS адресуется содержимым: уже существующий валидный
blob с тем же SHA-256 повторно используется без второй физической копии.

Порядковый номер проекта выделяется транзакционно. Если имя свободно без учёта
регистра, оно сохраняется. При конфликте добавляется суффикс
` (импорт <порядковый номер>)`; если занят и он, добавляется дополнительный
числовой суффикс. Длинное исходное имя обрезается только настолько, чтобы итог
оставался в доменном лимите.

Повторный импорт того же готового архива после завершённой операции создаёт ещё
один самостоятельный project ID, порядковый номер и при конфликте новое имя.

## Provenance и совместимость

Хранилище schema 5 добавляет неизменяемую таблицу `project_imports`. В одной
транзакции с проектом она сохраняет ID операции, SHA-256 manifest и всего архива,
исходные project ID/revision/increment, диагностические версии исходной schema и
приложения, а также время и версию приложения-импортёра. Это связь
`restoredFrom`; она не превращает импортированную копию в продолжение истории
исходника.

Контракт архива остаётся `manifestFormat = 1` и `snapshotFormat = 1`. Импортёр
читает архивы M1-13, созданные при storage schema 4: значение
`sourceStorageSchemaVersion` сохраняется как provenance, а предметный snapshot
проверяется по версии формата. Перед импортом приложение штатно мигрирует целевой
`dataRoot` до schema 5. Неизвестный manifest/snapshot format отклоняется до
публикации проекта.

## Проверка ZIP до публикации

Архив копируется в принадлежащий операции staging и полностью проверяется. Для
manifest и snapshot требуется канонический JSON без неизвестных полей и
повторяющихся properties. Проверяются detached checksum manifest, exact inventory,
размер и SHA-256 каждого payload, согласованность проекта, жгутов, вложений и
закреплённых характеристик. Лишние и неуказанные blobs запрещены.

Защитные пределы формата 1:

- готовый ZIP — не более 4 ГиБ;
- от 3 до 4096 ZIP entries, включая `manifest.json` и `manifest.sha256`;
- имя entry — не более 512 символов, NFC и только безопасный относительный путь;
- `manifest.json` — не более 1 МиБ, `project/snapshot.json` — не более 64 МиБ;
- один attachment blob — не более 25 МиБ;
- payload по manifest — не более 4 ГиБ;
- коэффициент распаковки — не более 100:1 для каждой entry и архива в целом;
- не более 100 жгутов и действующие доменные лимиты полей проекта.

Запрещены абсолютные пути, `..`, пустые сегменты, обратная косая черта, двоеточие,
управляющие символы, directory entries, symlink/reparse entries, duplicate и
case-colliding имена. Архивы с битым hash, несовместимой версией, traversal,
неполным или лишним payload отклоняются без видимого проекта.

## Атомарность и crash recovery

После полной проверки внутри `dataRoot` остаются только принадлежащие операции
staging и durable recovery journal. Проверенные immutable blobs публикуются до
SQLite-транзакции; проект, его дочерние записи и provenance становятся видимыми
одним DB commit.

Если процесс штатно получает ошибку до commit, транзакция откатывается, новые
неиспользуемые blobs удаляются, staging и journal очищаются. После аварийного
обрыва следующий обычный запуск до старта web-хоста просматривает журналы. Для
операции без DB commit он удаляет только принадлежащие ей orphan blobs, если на
них уже не ссылается БД или другой журнал, и очищает staging. Для уже
зафиксированного проекта он проверяет provenance и количество дочерних записей,
сохраняет результат и завершает отложенную очистку. Подозрительный reparse path
не удаляется принудительно и приводит к fail-closed диагностике.

## Проверка и то, что не входит

`ProjectImportIntegrationTests` проверяет независимую копию с двумя жгутами,
remap project-owned ID, `revision = 0`, пустую историю, provenance, повторный и
конкурентный импорт, повторное использование CAS и rollback до DB commit. Также
проверяются повреждённый checksum, отсутствующий и лишний payload, небезопасный
путь, case collision, несовместимый format и неканонический manifest.
`ServerOptionsTests` проверяет offline CLI и несовместимые режимы. Полный набор
автоматических проверок M1-14: 97 профильных и 350 тестов .NET; frontend: 35/35.
Штатный
сценарий: `scripts/test-m1-14.ps1`.

M1-14 не реализует слияние или обновление существующего проекта, разрешение
предметных конфликтов, перенос command/version history, импорт backup всего
хранилища и криптографическую проверку подлинности целиком подменённого архива.
Полнота компонентов, шаблонов, схемы и чертежа появится вместе с их
предметными моделями в M2/M4. Сквозная проверка переносимого приложения,
обновления schema, экспорта и импорта относится к M1-15.

# M0-04: Windows-оболочка, хранение и упаковка

Статус: завершено 2026-09-12. Зависимости: M0-01–M0-03. Это ограниченная
проверка архитектурных рисков, не приложение V1 и не итоговое ТЗ.

## Проверенные условия

- Целевая система V1 — Windows, работа на одном компьютере и передача полного
  установщика для обновления без потери проектов.
- Web-интерфейс и Canvas должны переноситься в будущий LAN-вариант.
- Программа, проекты, вложения и резервные копии физически разделяются.
- Перед миграцией создаётся проверяемая копия; восстановление создаёт отдельный
  проект и не заменяет исходный.

На проверенном компьютере доступны .NET SDK 8.0.407, ASP.NET Core Runtime 8.0.14
и Evergreen WebView2 Runtime 152.0.4191.66. Rust/Cargo, системные Node/npm,
Inno Setup, NSIS, WiX и локальные NuGet-пакеты WebView2/SQLite не обнаружены.
Новые зависимости из сети в эксперимент не загружались.

## Сравнение оболочек

| Вариант | Достоинства | Ограничения | Решение M0-04 |
|---|---|---|---|
| .NET + WebView2 | Нативный Windows-хост, существующий Canvas/JS, прямой путь к ASP.NET API для LAN | SDK WebView2 нужно добавить и проверить; среда выполнения должна поставляться установщиком | Основной кандидат M0-05 |
| Electron | Самодостаточная web-среда и зрелая упаковка | Крупнее пакет; Node/npm и нативный SQLite усложняют сборку | Резервный вариант |
| Tauri | Малый размер и системный WebView2 | Требует отсутствующих Rust/Cargo/MSVC; всё равно зависит от WebView2 | Не выбирать для V1 без новой причины |
| Локальный ASP.NET + браузер | Простой офлайн-прототип, почти прямой путь к LAN | Нет полноценной desktop-интеграции | Проверочный хост, не финальная оболочка |

Рекомендация для M0-05: модульный монолит на .NET, узкий API команд приложения,
web UI на Canvas и WebView2 в Windows-оболочке. Web-коду не давать прямой SQL или
произвольный доступ к файлам. В LAN-версии тот же контракт становится сетевым API;
SQLite нельзя открывать нескольким клиентам как общий файл на сетевом диске.

## Эксперимент хоста и упаковки

`experiments/m0-04/host` — минимальный ASP.NET Core-хост. Он слушает случайный
порт только на `127.0.0.1`, отдаёт web UI и сообщает раздельные пути программы и
данных. Скрипт `build-package.ps1` создаёт ZIP в игнорируемом каталоге `build/`.

Framework-dependent пакет содержит 7 файлов, 177 420 байт (0,17 МиБ). Он собран,
упакован, распакован в чистый каталог и запущен оттуда. HTTP `/` вернул 200,
`/runtime-info` подтвердил отдельный каталог данных. Первая проверка выявила две
ошибки: зависимость от текущего каталога и системного Event Log. После исправления
хост запускается из произвольного каталога с консольным журналом.

Этот ZIP не является установщиком и требует установленный ASP.NET Core Runtime 8.
Самодостаточный офлайн-пакет в текущей среде собрать нельзя: runtime pack отсутствует.
WebView2 SDK также не подключён, поэтому нативное окно проверяется в M1 после
фиксации версий зависимостей. Наличие runtime на этом ПК не доказывает чистую Windows.

Для V1 предлагается полный EXE-установщик Inno Setup с постоянным AppId. Новая
версия обновляет файлы программы, но не удаляет каталог данных. Установщик должен
включать или проверять .NET Runtime и WebView2; автоматическая загрузка обновлений
из сети в V1 не требуется. Цифровая подпись и канал обновления — отдельное решение
до выпуска, а не условие этого эксперимента.

## Эксперимент хранения

`experiments/m0-04/storage` использует синтетические JSON-данные и встроенные
модули Node.js. Он проверяет требуемое поведение до выбора SQLite-схемы:

- отдельные `program-data` и `user-data`;
- неизменяемые ревизии с атомарной публикацией;
- резервную копию с SHA-256 перед миграцией;
- миграцию глубокой копии и публикацию только после проверки;
- сохранность оригинала при ошибке миграции;
- восстановление под новым ID без изменения исходного проекта;
- отказ при повреждении резервной копии.

Все 7 тестов прошли. Демонстрация выполнила миграцию schema 1→2 и восстановила
отдельную копию schema 1. Это контракт поведения, не формат V1: SQLite, вложения,
дневное расписание, ротация и переносимый ZIP проекта остаются карточками M1.

## Вывод и следующий шаг

Риски локального запуска, разделения данных, миграции и восстановления имеют
рабочие решения. M0-05 должен утвердить стек и версии, записать лицензии,
численные цели производительности и разбить M1 на проверяемые карточки. Перед M9
потребуется повторить установку, обновление и восстановление на чистой Windows.

# M0-04R: переносимый web-интерфейс, хранение и упаковка

Статус: завершено 2026-09-12. Зависимости: M0-01–M0-03. Это ограниченная
проверка архитектурных рисков, не приложение V1 и не итоговое ТЗ.

Архитектурная часть пересмотрена 2026-09-12 по прямому требованию владельца:
нужен обычный web-интерфейс, пригодный для будущей крупной системы, и возможность
передать приложение ZIP-архивом на другой компьютер. Эксперимент хранения сохранён.

## Проверенные условия

- Целевая поставка V1 — self-contained Windows x64 ZIP, работа на одном компьютере
  в обычном браузере и обновление без потери проектов.
- Выбран контракт, при котором web-интерфейс, Canvas и HTTP API можно перенести в
  будущий LAN-вариант без WebView; сам LAN-режим экспериментом не проверялся.
- Файлы программы отделяются от каталога пользовательских данных. Внутри данных
  проекты и резервные копии имеют отдельные каталоги; модель вложений остаётся M1.
- Перед миграцией создаётся проверяемая копия; восстановление создаёт отдельный
  проект и не заменяет исходный.

На проверенном компьютере доступны .NET SDK 8.0.407 и ASP.NET Core Runtime 8.0.14.
Rust/Cargo и системные Node/npm не нужны на целевом компьютере. Для первой
self-contained сборки официальный runtime pack .NET был загружен с NuGet;
готовый ZIP не требует .NET, Node.js, WebView2 или интернета.

## Пересмотр оболочки

| Вариант | Достоинства | Ограничения | Решение M0-04R |
|---|---|---|---|
| ASP.NET Core + обычный браузер | Один web-клиент локально и в LAN, существующий Canvas/JS, без desktop API | Нужен локальный сервер и установленный браузер | Выбрано владельцем |
| .NET + WebView2 | Нативное окно для web-клиента | Создаёт отдельную desktop-оболочку и дополнительную зависимость | Исключено из основной архитектуры |
| Electron | Самодостаточная web-среда и зрелая упаковка | Крупнее пакет; Node/npm и нативный SQLite усложняют сборку | Резервный вариант |
| Tauri | Малый размер и системный WebView2 | Требует отсутствующих Rust/Cargo/MSVC; всё равно зависит от WebView2 | Не выбирать для V1 без новой причины |

Рекомендация для M0-05: модульный монолит на .NET, узкий API команд приложения и
web UI на Canvas в обычном браузере. Web-коду не давать прямой SQL или
произвольный доступ к файлам. В LAN-версии тот же контракт становится сетевым API;
SQLite нельзя открывать нескольким клиентам как общий файл на сетевом диске.

## Эксперимент хоста и упаковки

`experiments/m0-04/host` — минимальный ASP.NET Core-хост. Он слушает случайный
порт только на `127.0.0.1`, отдаёт web UI и сообщает раздельные пути программы и
данных. Скрипт `build-package.ps1` создаёт ZIP в игнорируемом каталоге `build/`.

Первый framework-dependent пакет имел размер 0,17 МиБ, но требовал установленный
.NET и потому не отвечал новому требованию. Пересобран self-contained win-x64 ZIP:
91,44 МиБ в распакованном виде и 39,60 МиБ в ZIP, включая манифест; пакет содержит
один основной EXE и web-файлы. Он распакован и
запущен при `DOTNET_MULTILEVEL_LOOKUP=0` и несуществующем `DOTNET_ROOT`.
HTTP `/`, `/api/v1/health` и `/api/v1/runtime-info` вернули 200. Первая проверка выявила две
ошибки: зависимость от текущего каталога и системного Event Log. После исправления
хост запускается из произвольного каталога с консольным журналом.

ZIP приложения содержит семь файлов: сервер, web UI, VERSION и SHA-256 манифест
с записями для остальных шести файлов. Манифест предназначен для ручной
проверки целостности файлов; автоматическая проверка и подпись остаются M1. Проекты
хранятся отдельно и передаются собственным экспортным архивом. Обновлять нужно
заменой файлов приложения после backup, без распаковки поверх живой базы.
Проверка на физически другом/чистом Windows-компьютере остаётся условием M1/M9.

## Эксперимент хранения

`experiments/m0-04/storage` использует синтетические JSON-данные и встроенные
модули Node.js. Он проверяет требуемое поведение до выбора SQLite-схемы:

- отдельные `program-data` и `user-data`;
- неизменяемые ревизии с атомарной публикацией;
- резервную копию с SHA-256 перед миграцией;
- миграцию глубокой копии и публикацию только после проверки;
- сохранность оригинала при ошибке миграции;
- восстановление под новым ID без изменения исходного проекта;
- отказ при повреждении содержимого проекта в резервной копии или несогласованных
  критичных полях манифеста.

Все 7 тестов прошли. Демонстрация выполнила миграцию schema 1→2 и восстановила
отдельную копию schema 1. Это контракт поведения, не формат V1: SQLite, вложения,
дневное расписание, ротация и переносимый ZIP проекта остаются карточками M1.

## Вывод и следующий шаг

Риски web-запуска, разделения данных, миграции и восстановления имеют рабочие
решения. M0-05 должен утвердить точный стек и версии, записать лицензии,
зафиксировать базовые пути клиента/API, ограничить диагностические endpoints для
LAN и разбить M1 на проверяемые карточки. M1 также должен определить блокировку
единственного процесса для каталога данных, защиту изменяющих HTTP-команд и
атомарное резервирование ID при восстановлении. Перед M9
потребуется повторить распаковку, запуск, обновление и восстановление на чистой Windows.

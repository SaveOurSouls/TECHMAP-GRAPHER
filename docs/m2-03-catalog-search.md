# M2-03: индекс и API большого каталога

Статус: завершено 13 сентября 2026 года. Карточка реализует backend каталога для
50 000 и более канонических записей. Пользовательский интерфейс быстрого доступа,
избранное, недавние позиции и drag-and-drop входят в M2-04.

## Результат

Публикация снимка справочника теперь в одной `IMMEDIATE`-транзакции создаёт
сменяемую поисковую проекцию и только после этого переключает active head. История
канонических снимков сохраняется, а derived-индекс существует только для активного
снимка и поэтому не растёт с каждой версией импорта.

Поиск читает страницу непосредственно из SQLite и не восстанавливает весь снимок в
памяти. Реализованы:

- prefix full-text search через SQLite FTS5;
- точный поиск по исходному ключу/артикулу;
- фильтр по типам сущностей;
- составные фильтры `all` и `any`;
- операторы поля `eq`, `prefix`, `exists`, `missing`, `null`, `blank`;
- сортировки `relevance`, `source-key-asc`, `source-key-desc`,
  `entity-type-asc`;
- keyset pagination без `OFFSET`, до 100 записей на страницу, по умолчанию 40;
- отмена асинхронного SQLite-чтения через request cancellation token.

`missing`, JSON `null` и пустая строка остаются разными состояниями. Числа и
логические значения индексируются в каноническом текстовом виде; диапазонные
предметные фильтры появятся вместе с профилями баз M2-10–M2-13.

## Нормализация и допустимые данные

Нормализация выполняется в .NET до записи в SQLite: Unicode Form C, invariant
uppercase, удаление крайних и схлопывание внутренних пробелов. `ё` и `е` не
объединяются. Исходный ключ и исходный JSON остаются без изменений, поэтому
ведущие нули сохраняются.

FTS получает только выделенные приложением буквенно-цифровые токены. Синтаксис
FTS/SQL от клиента не передаётся. Запрос ограничен 256 символами и восемью
токенами; допускается не более восьми типов и восьми полевых условий.

Derived-индекс не сужает контракт канонического снимка. Одинаковые после
нормализации имена полей, включая `A`/`a`, хранятся отдельно по исходному порядку.
Имя поля длиннее 256 символов или имя, нормализация которого даёт пустую строку,
остаётся в проекции, но не участвует в lookup по имени. Scalar длиннее 32 767
символов сохраняет тип и доступен для `exists`, но не для `eq`/`prefix`. Полный
текст записи всё равно строится в пределах разрешённого канонического payload.

## Курсор

Курсор подписан HMAC и содержит source, ID и SHA-256 снимка, хеш запроса, размер
страницы, полную позицию сортировки и срок действия 30 минут. Изменение запроса,
фильтра, сортировки, размера страницы, source или байтов курсора даёт
`catalog_cursor_invalid`.

После публикации новой версии активная проекция заменяется. Продолжение старого
курсора получает `409 catalog_cursor_snapshot_changed`; интерфейс должен начать
выдачу заново и объяснить, что база обновилась. Это принятое поведение позволяет
держать один ограниченный индекс вместо проекций всех исторических снимков.

## HTTP API

Поиск:

```text
POST /api/v1/reference-sources/{sourceId}/catalog-searches
```

Тело содержит `text`, `exactSourceKey`, массивы `entityTypes` и `filters`,
`filterLogic`, `sort`, `pageSize` и необязательный `cursor`. Ответ содержит только
текущую страницу `items`, `snapshotId`, `snapshotSha256` и `nextCursor`. Полный
`COUNT(*)` намеренно не выполняется.

Сохранённые фильтры:

```text
GET    /api/v1/reference-sources/{sourceId}/saved-filters
POST   /api/v1/reference-sources/{sourceId}/saved-filters
PUT    /api/v1/reference-sources/{sourceId}/saved-filters/{filterId}
DELETE /api/v1/reference-sources/{sourceId}/saved-filters/{filterId}
```

Фильтр общий для локальной установки и принадлежит одному источнику. Имя уникально
внутри источника; одинаковое имя допустимо в разных источниках. Сохраняется
каноническая versioned query v1 с SHA-256: условия, типы, логика и сортировка.
Cursor, размер страницы и материализованный список ID в запись не входят.

GET требует cookie локальной сессии. POST/PUT/DELETE дополнительно защищены общим
Origin/CSRF middleware приложения.

## Schema 8, миграция и резервные копии

Schema 8 добавляет `reference_search_projections`, `reference_search_records`,
external-content `reference_search_fts`, `reference_search_fields` и
`reference_catalog_saved_filters`. Миграция 7→8 строит проекцию уже
опубликованного active snapshot внутри той же транзакции, в которой записывается
история schema 8. Ошибка откатывает миграцию целиком.

Проверка backup/restore сверяет active head с проекцией, заявленное и фактическое
число записей, число FTS docsize-строк и канонический JSON/hash/время сохранённых
фильтров. Интеграционный сценарий полного восстановления подтверждает поиск по
старой сохранённой версии после замены live-каталога.

## Производительность

Закреплённый тест создал 50 000 синтетических записей. Стенд: Windows x64,
.NET 10.0.12, 24 logical processors. Для каждого сценария выполнены пять
прогревов и 30 измерений асинхронного SQLite-запроса.

| Сценарий | p95, мс | max, мс |
|---|---:|---:|
| Пустая первая страница | 3,91 | 4,04 |
| Точный ключ | 3,62 | 4,44 |
| Полный текст | 9,16 | 9,38 |
| Поле `eq` | 11,78 | 12,06 |
| Поле `prefix` | 6,11 | 6,24 |
| Два условия `all` | 14,49 | 17,22 |
| Два условия `any` | 8,63 | 8,69 |
| Нет совпадений | 3,63 | 4,50 |
| Поздняя keyset-страница | 3,76 | 3,85 |

Общий p95 — 12,59 мс, max — 17,22 мс при бюджете p95 ≤ 100 мс и max ≤
200 мс. Публикация и построение индекса заняли 20,82 с. `EXPLAIN QUERY PLAN`
подтвердил B-tree `ix_reference_search_records_key` для точного ключа и
`ix_reference_search_fields_text` для полевого поиска.

## Проверки

Покрыты все сортировки и полный обход страниц без повторов/пропусков, `all`/`any`
и все операторы, кириллица и NFC/NFD, ведущие нули, FTS-shaped input, лимиты,
изменённый и слишком длинный cursor, смена active snapshot, миграция заполненной
schema 7, длинные/коллидирующие JSON-поля, CRUD/restart сохранённых фильтров,
повреждение проекции/FTS/filter hash и поиск после полного restore.

M2-04 использует эти API для видимого каталога, виртуализированного списка,
избранного, недавних объектов и перетаскивания.

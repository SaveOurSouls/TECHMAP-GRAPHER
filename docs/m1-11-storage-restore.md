# M1-11 — пробное и полное восстановление хранилища

Дата: 2026-09-12. Статус: реализовано ядро восстановления backup.

## Контракт восстановления

M1-11 использует тот же строгий reader/verifier, которым writer проверяет staging,
а retention читает опубликованные копии. До чтения содержимого проверяются физические
пути и lease backup-root. Проверка включает detached SHA-256 манифеста, закрытую
форму JSON без лишних и повторяющихся полей, лимиты количества и размера файлов,
canonical/case-unique пути, точный инвентарь, SHA-256 каждого файла, SQLite
`integrity_check`, `foreign_key_check`, строгую форму schema 1–4, ревизии проектов
и точное соответствие referenced CAS blobs.

Пробное восстановление принимает опубликованный backup и новый `recoveryRoot`.
В родительском каталоге создаётся приватный staging с уникальным маркером владения.
Он физически отделён от backup и рабочего `dataRoot` и получает собственный lease.
В staging последовательно записываются referenced CAS blobs, `app.db`, `READY` и
`CURRENT`; каждый файл публикуется write-through rename. После полной проверки
весь staging одним неперезаписывающим write-through rename становится запрошенным
`recoveryRoot`; это единственное действие, которое делает запрошенный корень
видимым. Гонка с другим владельцем не удаляет и не изменяет его каталог.
Backup повторно проверяется после копирования. Ошибка удаляет только staging с
точным маркером текущей операции; рабочее хранилище не меняется. Так можно
проверять backup schema 1–4.

Полное восстановление является отдельной offline-операцией для текущей schema 4:

1. `PrepareFullRestoreAsync` повторно проверяет backup и текущее хранилище.
2. План содержит одноразовый plan ID, backup ID и SHA-256 manifest, канонический
   `dataRoot`, имя текущего поколения, SHA-256 БД и fingerprint БД, ревизий и blobs.
3. `RestoreAsync` принимает точную строку подтверждения из этого плана. Изменение
   backup или текущего состояния делает план недействительным.
4. Операция получает эксклюзивный физический `DataRootLease`; запущенный server
   или другой restore блокирует её. Открытая SQLite БД дополнительно обнаруживается
   эксклюзивным file handle.
5. До candidate обязательно публикуется и повторно проверяется backup вида
   `pre-restore`, соответствующий подтверждённым schema/revisions/blobs. Ошибка
   backup отменяет restore.
6. В новом `generation-NNNNNNNN` сначала публикуются referenced CAS blobs, затем
   копируется и проверяется `app.db`; marker завершения связывает plan, backup и
   pre-restore backup, после итоговой проверки создаётся `READY`.
7. Backup ещё раз проверяется, после чего `CURRENT` заменяется Windows
   `MoveFileExW(REPLACE_EXISTING | WRITE_THROUGH)`. Это доступная Windows
   same-volume атомарная замена с write-through семантикой, без более сильного
   обещания directory fsync при полном отключении питания. Это commit point и
   последнее изменяющее действие; после него отмена не наблюдается, а активное поколение
   исключается из cleanup даже при ошибке сразу после системного rename.

Повтор той же подтверждённой команды после потерянного ответа проверяет marker,
исходный backup, pre-restore backup и активное поколение и возвращает исходный
успешный результат без второй копии или нового поколения.

Старое поколение и прежние blobs карточка не удаляет. Сбой до switch оставляет
прежний `CURRENT`, а незавершённый candidate удаляется best effort. Сбой процесса
после switch оставляет полностью проверенные DB/blobs/READY и новый валидный
`CURRENT`. Retention защищает последний успешный backup, последний `pre-update`
и последний `pre-restore`; минимальный лимит теперь равен трём.

## Проверки

`StorageRestoreIntegrationTests` проверяет dry-run без изменения live root,
отказ повреждённого backup, обязательное точное подтверждение, stale plan,
занятый data-root lease, успешный pre-restore и switch, конфликт существующего
blob, ошибку backup, отмену и повтор, а также границы до и после `CURRENT` switch.
Отдельно проверяются сбой и гонка публикации recovery-root, отказ от записи через junction
в `attachments` и исключение непосредственно после успешного rename `CURRENT`.
Регрессия backup/policy использует общий verifier и включает новый вид manifest.

Штатный запуск: `scripts/test-m1-11.ps1`. Скрипт выполняет проверки M1-10,
профильные restore/backup/policy тесты, полный Release build и полный набор .NET
тестов. Фактические числа успешных тестов фиксируются в `docs/work-state.md` после
прогона.

## Границы карточки

В M1-11 нет startup/UI orchestration: server должен быть остановлен, а команда
обслуживания должна явно вызвать prepare/restore. Подключение backup policy до
миграции и candidate migration остаются M1-12. Экспорт/импорт одного проекта и
ID remap остаются M1-13/M1-14. Старый backup schema 1–3 разрешён для dry-run,
но полное восстановление требует отдельной миграции в M1-12 и сейчас отклоняется.

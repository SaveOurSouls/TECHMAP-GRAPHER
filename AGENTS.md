# Правила автономной работы задач

- Переданный в эту задачу конкретный запрос является командой начать работу. Не
  отвечать встречным «чем помочь?» и не ждать отдельного запуска от пользователя.
- Самостоятельно принимать обычные технические решения в пределах указанной
  карточки, читать состояние репозитория и продолжать до проверяемого результата.
- Не задавать уточняющих вопросов, если разумное безопасное предположение позволяет
  продолжить. Останавливаться только при реальном внешнем блокере, который нельзя
  устранить в задаче.
- Если задача аналитическая, завершить весь заказанный анализ. Если задача включает
  реализацию, выполнить код, тесты и документацию в назначенной рабочей копии.
- Не расширять область на следующую карточку и не менять файлы, закреплённые за
  другой параллельной задачей.
- Любое законченное решение после успешных обязательных проверок самостоятельно
  оформлять содержательным Git-коммитом без дополнительного разрешения пользователя.
  Не накапливать несколько готовых срезов без коммитов.
- Пользователь явно разрешил локальные коммиты всех готовых проверенных изменений
  и их отправку в настроенный удалённый репозиторий
  `git@github.com:SaveOurSouls/TECHMAP-GRAPHER.git` без повторного подтверждения.
  Не оставлять готовый код только в рабочем дереве. Новый адрес репозитория требует
  отдельного явного поручения.
- Перед переключением ветки, очисткой рабочей копии, передачей следующей карточке
  или любым действием с риском утраты кода сначала проверить и закоммитить все
  готовые изменения. Это постоянное разрешение пользователя действует для всех
  последующих задач в этом репозитории и не требует повторного согласования.
- Не коммитить состояния с падающими обязательными проверками, временные файлы
  сборки, локальные данные, секреты и диагностические артефакты. Всегда сообщать
  хеш коммита, выполненные проверки и оставшиеся ограничения.
  Cn обозначает номер скриншота, который был добавлен к поручению. На него нужно ссылаться и находить указанную проблему, делать оценку

## Ведение проекта через Markdown

- Перед новой карточкой читать `docs/project-workflow.md`, `status.md`, нужные
  `tasks/*.md`, `docs/requirements.md` и действующие ADR. Пользовательское
  поручение имеет приоритет над этими файлами.
- Новое поведение связывать со стабильным ID требования `REQ-###`, а работу —
  с отдельной карточкой в `tasks/`. Восстановленные из кода требования и
  предположения не выдавать за явно утверждённое владельцем ТЗ.
- В параллельных чатах заранее обозначать владельца файлов карточки. Не
  включать в свой коммит чужие незавершённые изменения; использовать явные пути
  при `git add` и сверять staged diff.
- `status.md` отражает последний проверенный срез, а не обещание готовности
  незавершённой работы. ZIP собирать после фиксации нужных изменений и проверять
  по правилам `docs/project-workflow.md`.
